## Dymka ARG

##### Игра в альтернативной реальности, созданная как авторский проект.

ARG *(Игра с альтернативной реальностью)*, прошедшая на канале Daniel Myslivets, разработана мной совместно с командой которой я руководил.

Мои основные роли включали:
- разработку вселенной и проработку лора (совместно с художниками),
- проектирование технической части,
- организацию и руководство разработкой.

Проект был разделён на несколько актов. Ниже приведена краткая информация о мини-проектах, реализованных в каждом из них.

### Технические решения в ARG.

#### Акт 1

Для первого акта нам нужно было сделать импровизированное RDP подключение в браузере, для этого мы сделали страничку со входом в стиле Windows 10, требующую пароль. После правильного ввода пароля - php рендерил уже другую страницу, с powershell терминалом. Терминал отправлял запрос каждой команды на сервер, получал ответ и отрисовывал в окошке.

Сервер и все необходимые команды были сделаны используя express.js

#### Акт 2

Для второго акта нам нужно было буквально занятся вандализмом на сайте с движком викимедиа. Это было реализовано через before блоки с наложением поверх изображений.

Так люди нашли блог на вордпрессе. Нам нужен был пользователь получающий доступ к черновым постам в блоге, однако не имеющих каких либо иных прав, чтобы что-то не пошло не так.
Для этого мы написали плагин для вордпресс который ограничивал пользователя Kiffa во всём, но не учли метки к постам. Исправили в последствии.

#### Акт 3

Для третьего акта мы деактивировали сайт блога, оставив заглушку провайдера «MDTK». Задача игроков была позвонить в тех. поддержку где их ждал ад из телефонного меню. Огромное количество разветвлений которые приходилось долго ждать.

Была разработана схема телефонного меню:

Дальше распределены голоса по отделам, обработан звук и конвертирован в формат подходящий для FreePBX.

Само телефонное меню было сделано набором инструкций для Asterisk, который преобразовывался из yaml файла самописным скриптом.

```yaml
techbegin:
    1: cryaboutit
    2: KDEFreeBSD
    3: enterSIDORCode
    4: WelcomeYUR
    5: ipcollection
    6: crisis
    %timeout: Repeat()
```

Здесь указаны названия файлов и при нажатии на клавишу - пользователя переводило к аудиофайлу и, соответственно, меню указанному под таким же названием.

Далее настроили SIP, привязали номера и пустили в сеть.

#### Акт 4

Для четвёртого акта ARG была разработана система «импровизированного чата» — псевдо-диалога, в котором сервер генерирует заранее подготовленные ответы, создавая эффект живого общения.
Логика была вынесена в единый API-эндпоинт вида: `/vrc/{functionName}`

Каждая публичная функция, экспортируемая из `vrc.js`, автоматически становилась доступным эндпоинтом. Ниже — финальный интерфейс системы.

##### Основные API-методы

**1.** `availableAddress ? userId`

Возвращает список чатов, доступных пользователю:

- название чата
- его текущий онлайн
- идентификатор

**2.** `getChatInfo ? uuid & chatId`

Возвращает ту же структуру, но только для одного конкретного чата.

##### Работа с историей и контекстом

**3.** `getChatHistory ? uuid & chatId`

Выдаёт полную историю диалога (сообщения, направление (вход., исход.)).

**4.** `getRandomQuestions ? uuid & chatId`

Генерирует 4 случайных вопроса, доступных пользователю в текущем состоянии диалога.
Особенности:

- вопросы **не повторяются** — выбираются с учётом уже заданных;
- каждый вопрос имеет «уровень» появления (stage);
- уровень растёт каждые 2 заданных вопроса;
- это создаёт ощущение «прогрессии» и развития разговора.

**5.** `getMood ? chatId`

Каждый вопрос имеет позитивный или негативный эффект, влияющий на настроение собеседника.
Функция возвращает актуальное состояние:

`Sad | Neutral | Happy`

##### Задавание вопросов и отложенные ответы

**6.** `askQuestion ? uuid & chatId & questionId`

Фиксирует выбор вопроса и возвращает **offset** — количество секунд, через которое нужно вызвать `resolveQuestion`.
Это создаёт эффект «задержки ответа», имитируя typing delay или обдумывание.

**7.** `resolveQuestion ? uuid`

Отправляет пользователю подготовленный ответ.
Отработает только если прошло достаточно времени после `askQuestion`;
если нет — вернёт ошибку *“not enough time passed”*.

**8.** `isPendingAnswer ? uuid`

Используется при открытии чата на фронтенде.
Возвращает:

- `pending: Boolean`
- если ожидается ответ — оставшийся `offset` до возможности вызвать `resolveQuestion`.

**9.** `finishReturningFile ? uuid & chatId`

Если пользователь задал вопрос с `id === "final"`, этот эндпоинт отправляет файл, необходимый для прохождения акта.

#### Акт 5

В пятом акте я создал пародию на **Hacknet**: полноценную терминальную среду, в которой игрок взаимодействует с «виртуальной ОС» через симуляцию терминала.
И фронтенд, и бэкенд были реализованы на Svelte 5 менее чем за 7 часов.

##### Фронтенд

**Кастомный терминальный интерфейс:**

Я реализовал терминал «с нуля», без библиотек — с полностью собственным обработчиком ввода.

Поддержано:

- перемещение курсора: **Home/End**, **←/→**;
- редактирование строки: **Backspace/Delete**;
- навигация по истории: **↑/↓**;
- управление выводом: **PageUp/PageDown**;
- **Ctrl-комбинации** (Ctrl+C, Ctrl+V, Ctrl+X);
- вставка из буфера;
- корректная работа с Unicode.
- подсветка цветами через собственные placeholder-теги (`{{g}}`, `{{b}}` и т.д.).

**Автокомплит по `TAB` работает так же, как в UNIX**

- циклический перебор вариантов;
- команды + файлы зависят от текущего домена и директории;

**Функция SubmitCommand (Связь фронтенда и бекенда):**

Каждая команда передаётся на сервер вместе с **контекстом сеанса**:

```js
context = {
    path,
    domain: host,
    username,
    password
}
```

Это позволяет бэкенду знать:

- где «находится» игрок (`path`);
- к какому «серверу» он подключён (`domain`);
- под кем он авторизован (`username`);
- какой используется пароль (`password`).

После выполнения команды фронтенд:

- сохраняет собственный **prefix** вида
  `{{g}}user@domain{{/}}:{{b}}/current/path{{/}}$`
- следом к прошлой строке добавляет отправленную команду и записывает её в историю;
- парсит бинарный ответ:
  - файл → скачивание;
  - текст → вывод;
  - JSON → изменение контекста и вывод.

При получении `response.context` терминал обновляет внутреннее состояние, например:

- смена директории
- смена домена
- обновление логина/пароля
- обновление автокомплита

То есть контекст сеанса постоянно мутирует, имитируя настоящую работу в терминале.

##### Бекенд

**Виртуальная ОС**

Я реализовал собственное мини-ядро CLI-команд:

Поддержано:

* `ls` — вывод содержимого виртуальной директории
* `cd` — перемещение по путям
* `open` — чтение текстовых файлов
* `download` — возврат бинарных данных
* `probe` — «сканирование» сетевого узла
* `connect` — имитация SSH-подключения
* `SSBrute` — псевдо-брутфорсер пароля

Команды меняют состояние контекста (путь, домен, доступные файлы, статус подключения), что позволяет создавать цельный игровой процесс, построенный на командных сценариях.

**Разделённые файловые системы**

Для разных доменов существуют свои директории — сервер как бы «поднимает» разные компьютеры внутри ARG.

**Сканирование и сетевые действия**

`probe`, `connect`, `SSBrute` создают иллюзию «сетевой безопасности»:

- задержки исполнения,
- псевдо-портскан,
- отчёты о найденных сервисах,
- сценарии успешного/неуспешного подключения.

**Поддержка бинарных ответов**

Если команда должна вернуть файл — сервер отправляет `Content-Disposition: attachment`, а фронтенд автоматически инициирует скачивание.
